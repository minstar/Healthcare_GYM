# STaR Baseline — What Was Reimplemented, Every Deviation, and What the Rebuttal May Claim

**Reference method**: STaR — Self-Taught Reasoner (Zelikman, Wu, Mu & Goodman,
"STaR: Bootstrapping Reasoning With Reasoning", NeurIPS 2022, arXiv:2203.14465).

**Reference code**: `github.com/ezelikman/STaR`. **It was NOT run, and it was not
cloned as a runnable dependency.** That release is JAX 0.2.12 /
`mesh-transformer-jax` / GPT-J-6B on TPU pods driven by Ray. None of that exists
on this cluster (B200 / CUDA / PyTorch 2.9.1 / sglang 0.5.9), and no part of it
is invoked by anything in this arm.

> **Nothing produced by this arm may be described, in the rebuttal or anywhere
> else, as output of the authors' script.** What is reproduced is the
> ALGORITHM — sample, filter on correctness, fine-tune, repeat — against this
> paper's own environment, task pool and scorers. Every deviation is listed
> below and must be quoted, or paraphrased with equivalent specificity, wherever
> the number is reported.

**Port target**: this repository. New files, all owned by this arm:

| File | Role |
|---|---|
| `Healthcare_GYM/scripts/rebuttal/star_generate.py` | one generation pass: roll out, score, filter, write SFT data, report acceptance |
| `Healthcare_GYM/scripts/rebuttal/star_iterate.py` | the outer loop: generate → filter → SFT → repeat; per-iteration stats and curve |
| `hcgym_rebuttal/runs/train_star.slurm` | sbatch driver, same harness conventions as the other arms |
| `Healthcare_GYM/tests/test_star_baseline.py` | 38 no-GPU tests |

Existing files used **unmodified**: `bioagents/evaluation/agent_runner.py`
(rollouts), `bioagents/evaluation/rewards.py` (composite reward),
`scripts/verl/reward_fn.py` (the RL arms' scorer, imported read-only),
`bioagents/training/sft_trainer.py` + `bioagents/data_pipeline/sft_generator.py`
(the SFT half), `runs/common_env.sh`.

---

## 1. Why this arm exists

Two gaps in the submitted paper motivate this arm. It shows no evidence separating
a real capability gain from the policy learning to satisfy the reward's surface
form, and the RL methods it names in Section 2.3 — STaR among them — are never
compared against.

STaR isolates the null hypothesis behind both gaps:

> **Is reinforcement learning needed at all, beyond supervised imitation of the
> rollouts that happened to succeed?**

If this arm matches the RL arms, the paper's contribution claim is in serious
trouble and has to be restated. The arm is therefore built to be able to produce
that result: full-parameter fine-tuning (not LoRA), the same backbone, the same
task pool, the same turn budget, and a rollout budget matched to the RL arms
exactly.

---

## 2. What was reimplemented (faithful to the paper)

1. **The outer loop, as Algorithm 1.**
   `M_0 ← base;  for n: rollouts ← M_{n-1};  D_n ← {correct};  M_n ← train(M_0, D_n)`.
   Three iterations by default.
2. **Fine-tune from the ORIGINAL model every iteration**, not from the previous
   iteration's checkpoint — the paper's stated choice, to avoid overfitting.
   `--init-from base` (default); `--init-from previous` is the continual variant.
3. **The dataset is the current iteration's accepted set**, not the union across
   iterations: the rationales are regenerated by the improved policy each round.
   `--dataset-scope current` (default); `accumulated` gives the union.
4. **One retained rationale per problem per iteration.** STaR generates one
   rationale per problem. `k` samples are drawn here only to match the RL arms'
   rollout budget (§5), so keeping all of them would additionally re-weight the
   training set toward whichever problems happen to be easy — an easy task would
   contribute `k` near-duplicates and a hard one at most 1.
   `--max-accepted-per-task 1` (default); `0` keeps everything.
5. **Filtering on correctness, not on a shaped reward** (§4).
6. **Temperature-1.0 sampling** during generation. The paper's greedy decoding
   would make all `k` samples of a problem identical and destroy the point of a
   `k`-sample budget.

## 3. Deviations from Zelikman et al. 2022 (quotable list)

None of these is cosmetic.

1. **Different code, different framework, different scale.** Reimplemented in
   PyTorch/TRL/sglang against a 9B-class instruction-tuned backbone, not JAX +
   GPT-J-6B on TPU. No line of the authors' code is executed.
2. **Multi-turn tool-use trajectories, not single-turn rationales.** STaR's unit
   of training data is `(question, rationale, answer)` from one forward pass.
   Here it is a whole GYM episode: system prompt + task ticket + up to
   `MAX_TURNS=5` assistant turns interleaved with real tool observations from the
   828K-passage medical knowledge base. "Keep the rationale" therefore means
   "keep the entire interaction trace", including which evidence the policy chose
   to retrieve.
3. **No rationalization.** Deliberate; see §6.
4. **Correctness comes from the environment's graders, not from a string match
   against a gold arithmetic answer.** The GYM tasks are 33% multiple-choice and
   67% open-ended, so "correct" is defined by the scorers this paper already
   uses (§4).
5. **The base policy is instruction-tuned and already emits tool calls.** STaR
   bootstrapped a base LM with few-shot prompting; the first iteration here
   starts from a policy that can already act, so iteration 0's acceptance rate is
   not comparable to the paper's.
6. **Loss is not masked to assistant tokens.** See §8.1 — a limitation inherited
   from the shared trainer, not a design choice, and it must be disclosed.
7. **Images are not delivered to the policy during generation.**
   `AgentRunner.run_task` builds string-only messages, so an image-grounded task
   reaches the policy as a file path in the ticket, not as pixels. 540/3390
   (15.9%) of the train pool is `multimodal_vqa`. The RL arms' verl rollout path
   *does* carry images (`data.image_key=images`). Two consequences, both of which
   must be stated wherever the number appears:
   * STaR's acceptance rate on that slice is a floor, not the policy's real
     ability; `gen_stats.json → by_source_domain` reports it separately so the
     size of the effect is visible rather than assumed.
   * `--pool full_4modality_clean_textonly` (2865 train / 788 test) runs the
     variant that spends no budget on unseeable tasks. The RL arms have matching
     text-only runs (`q9btxt`, `glm9b` in `runs/launch_backbones.sh`), so that
     comparison is available and is the cleaner one if the multimodal slice
     turns out to dominate the gap.
8. **`--no-think` by default**, matching `runs/eval_agentic.slurm`, so the
   trajectories STaR trains on come from the same tool surface every condition in
   the rebuttal table is evaluated with.

## 4. The acceptance signal — the decision that matters

### The problem

The GYM's composite reward weights **six** dimensions
(`bioagents/evaluation/rewards.py::compute_composite_reward`):

| accuracy | format | process | safety | coherence | assertion |
|---|---|---|---|---|---|
| 0.25 | 0.10 | 0.20 | 0.20 | 0.10 | 0.15 |

(Note for the writeup: the reward is **6D**, not 5D. `scripts/verl/reward_fn.py`,
which is what the RL arms actually optimise, is a *different and much sparser*
function — binary accuracy plus a +0.1 `Answer: X` format bonus minus 0.2 per
hallucinated tool call, optionally cosine-length-shaped. Do not conflate the two
in the rebuttal.)

Accuracy is 0.25 of the composite; format + process + coherence + safety are
0.60. Accepting on the composite would select trajectories for being
well-presented — which would make this baseline *exhibit* the very confound it
exists to rule out instead of testing for it.

### The measurement

`tests/test_star_baseline.py::test_composite_reward_ranks_a_wrong_fluent_rollout_above_a_correct_terse_one`
runs the live scorer over the first 200 multiple-choice tasks of the real
training pool, with each task's own `expected_actions` and `nl_assertions`,
comparing a **correct terse** answer against a **wrong fluent** one:

```
composite inversion on 105/200 real tasks (52.5%); mean(wrong-correct) = -0.001
```

On more than half of real training tasks the composite ranks the **wrong**
rollout **above** the **correct** one, and the mean margin between them is
essentially zero. At this presentation gap the composite carries almost no net
accuracy signal. A single concrete pair (pool task `medqa_00045`, its own
criteria):

```
correct, terse    total=0.600   acc=1.00 fmt=0.30 proc=0.49 safe=0.96 coh=0.20 asrt=0.07
wrong,   fluent   total=0.625   acc=0.00 fmt=1.00 proc=0.79 safe=1.00 coh=0.95 asrt=0.49
```

### The decision

**Default `--accept-on qa_accuracy`, threshold 1.0** — correctness alone, from
`AgentRunner._compute_qa_accuracy`, the environment's own grader for the answer
submitted through `submit_answer`.

This is also what the sibling baseline already in this repo does:
`ReflexionConfig` sets `qa_success_threshold = 1.0` and leaves
`reward_success_threshold = None`, commented *"do NOT use the shaped composite
reward as a pass/fail signal"*.

### Both are supported and both are reported

Every rollout is scored on **every** signal and the scores are persisted, so the
composite-accepted variant costs a file read rather than a second 10k-rollout
run:

```bash
python scripts/rebuttal/star_generate.py --refilter-from <iter_00/gen> \
    --accept-on composite_reward --out-dir <iter_00/gen_composite>
```

`gen_stats.json → acceptance_if_accepted_on` additionally reports the
counterfactual acceptance rate under every signal at its own threshold, in every
run, so the rebuttal can say how much the choice of signal actually mattered
without running anything extra.

| signal | what it is | default threshold | accuracy-only |
|---|---|---|---|
| `qa_accuracy` | env's `submit_answer` grader (exact letter for MC) | 1.0 | yes — **default** |
| `accuracy` | the composite's accuracy dimension alone (`accuracy_reward_soft`): exact match for A–E, normalised match for short answers, token-F1 for long. Accepts correct answers that never reached `submit_answer` | 0.5 | yes |
| `verl_acc` | `reward_fn.compute_score(...)["acc"]` — the binary readout the RL arms are compared on, recomputed on a reconstructed verl-style transcript | 1.0 | yes |
| `composite_reward` | the full 6D composite | 0.5 | **no** |
| `action_score` | expected-vs-actual tool-call completeness | 1.0 | no (1.0 by definition when a task lists no expected actions) |
| `verl_score` | `reward_fn`'s *shaped* score | 0.5 | no — recorded only; `reward_fn`'s own docstring says it is "NOT comparable across arms" |

`verl_acc` deserves a caveat: it is computed from a **reconstruction** of the
verl rollout string (`render_verl_solution` re-emits `<function=NAME>` /
`<tool_response>` markup around AgentRunner's structured turns). It is
semantically the same transcript, not a byte-identical replay. It is verified
against `reward_fn`'s own parsers in
`test_render_verl_solution_emits_markup_reward_fn_can_read` and agreed with the
GYM grader on every multiple-choice rollout in
`test_verl_acc_agrees_with_the_env_grader_on_multiple_choice`.

### Guardrail: an uninformative threshold cannot pass silently

If the acceptance rate lands below 2% or above 98%, `star_generate.py` prints a
banner and **exits 3**; `star_iterate.py` refuses to continue when that happens
at iteration 0, or whenever the rate is exactly zero. Near 0 there is nothing to
fine-tune on; near 1 the filter is not filtering and STaR has degenerated into
plain self-imitation. Either way the arm would be uninformative, so it stops
rather than training. A *high* rate at a later iteration is recorded and the loop
continues — that is the expected STaR endgame, a result and not a
misconfiguration.

## 5. Fair budget

The RL arms in `runs/train_hcgym.slurm` consume

```
|pool| x rollout.n x total_epochs  =  3390 x 3 x 3  =  30,510 rollouts
```

The STaR arm consumes

```
|pool| x samples_per_task x iterations  =  3390 x 3 x 3  =  30,510 rollouts
```

**Exactly equal, and that is why `SAMPLES_PER_TASK=3` and `ITERATIONS=3` are the
defaults.** `star_generate.py` computes both sides from `ROLLOUT_N` /
`TOTAL_EPOCHS` (which `train_star.slurm` pins to `train_hcgym.slurm`'s defaults),
prints them every run, and persists them to `gen_stats.json → budget` with a
`matched` boolean. Changing either default breaks the claim and the recorded
boolean will say so.

Three qualifications the rebuttal must carry:

* **Both figures are configured budgets.** A preempted RL run that never
  finishes 3 epochs consumes fewer; compare against what actually ran, using the
  RL arms' step counts.
* **The held-out probe is extra and is not part of that budget.** It is 200
  test tasks × 1 rollout per iteration (4 probes ≈ 800 rollouts, 2.6% on top).
  The RL arms' own validation is far larger — `test_freq=10` over the full
  850-task test split — so STaR's diagnostic overhead is strictly the smaller
  of the two and does not favour it.
* **Gradient budget is a different axis and is NOT matched.** The RL arms take
  ~1,450 optimiser steps at batch 7. STaR takes 3 × (2 epochs over |D_n|). SFT
  epochs, LR (1e-5) and effective batch (1 × 8 grad-accum × 7 GPUs) are this
  arm's own hyperparameters, carried at the repo's SFT defaults with no sweep.
  If the arm loses, "STaR was not tuned" is a live objection; say so up front
  rather than waiting for someone else to.

## 6. Rationalization — deliberately not implemented

STaR's second half feeds the known answer back as a hint on problems the model
failed, has the model produce a rationale that reaches that answer, and keeps the
rationale with the hint removed. **It is not implemented here.** The reasons, in
order of weight:

1. **It would manufacture exactly the pathology under investigation.** In a
   single-turn arithmetic setting the rationale is a derivation and the hint only
   changes the wording. Here the retained artifact is a full tool-use episode:
   *which evidence the policy searched for was chosen while the gold answer was
   in its context.* Training on those actions teaches answer-conditioned
   retrieval — right-for-the-wrong-reason behaviour that would inflate the
   arm's accuracy without any corresponding gain in clinical process. This arm
   exists to test for reward-format adaptation; building in a mechanism that
   produces a different flavour of the same defect would defeat it.
2. **Gold-in-context is already treated as a leak hazard in this repo.** The
   Reflexion baseline defines a `GoldAnswerLeak` exception for precisely this.
   Retaining hinted trajectories would need a scrub-and-verify pass (hint removal
   plus a check that the gold string appears in no tool argument or observation
   before the final submission), and an unverified scrub is worse than no
   rationalization at all.
3. **The paper's own evidence for it is in a setting that does not transfer.**
   Rationalization is reported on arithmetic and CommonsenseQA, where the
   rationale is short and answer-determined.

**Consequence for the claim, and it cuts one way:** rationalization only ever
fires on problems the policy failed, so it can only *add* training data.
This arm is therefore a **lower bound on STaR's dataset size**, which means:

* if STaR **matches** the RL arms here, that is a *strong* result against the
  paper — full STaR would only be stronger;
* if STaR **loses** here, that is *weak* evidence, because full STaR might close
  part of the gap. The rebuttal must not present a STaR loss as a settled
  refutation of the null hypothesis.

The trajectory format is forward-compatible: every record carries
`star.rationalized: false`, so a later rationalization variant is distinguishable
inside the same files without a format change.

## 7. What is held fixed with the other arms

| | RL arms (`train_hcgym.slurm`, `train_opsd.slurm`) | STaR (`train_star.slurm`) |
|---|---|---|
| backbone | `$BACKBONE` | same |
| task pool | `full_4modality_clean`, train split (3390) | same |
| turn budget | `max_assistant_turns=5` | `MAX_TURNS=5` |
| student GPUs | 7 | 7 (SFT half) |
| rollout budget | 30,510 | 30,510 |
| degenerate-response guard | on, `DEGENERATE_*` | same values |
| cosine length reward | ttopd / grpo_cosine only | **off, explicitly unset** |
| parameter update | full-parameter FSDP | full-parameter (`peft.enabled: false`) |
| held-out eval | `eval_agentic.slurm`, `MAX_TURNS=5` | same harness for the final model |

`train_star.slurm` unsets `COSINE_*`, `BT_OPD_*`, `HINT_OPD_*`,
`ADAPTIVE_DISTILL_*` and `OPSD_*` explicitly rather than assuming they are
absent, because `autoretry.sh` submits with `--export=ALL` and a stale variable
in the submitting shell would otherwise leak in. The `DRY_RUN=1` path enumerates
the live environment with `compgen -e` and prints any that survived as
`DRYRUN LEAKED …`.

Three SFT-config settings are load-bearing and are asserted by tests:

* **`qa_tasks_path: ""`** — `BioAgentSFTConfig` *defaults* it to
  `data/domains/medical_qa/tasks.json`, and `qa_tasks_to_sft` synthesises
  gold-answer demonstrations from it. Leaving the default would silently mix
  oracle answers into a baseline whose entire premise is that it sees only its
  own successful rollouts.
* **`peft.enabled: false`** — a LoRA-only STaR arm would lose on capacity, not
  on method.
* **`min_reward: 0.0`** — the acceptance test has already been applied by
  `star_generate.py`. `sft_trainer`'s own filter re-reads
  `max(final_reward, action_score)`, which is a *different quantity* from the
  acceptance signal; at 0.0 it is a pass-through over an already-filtered
  directory. The recorded `final_reward` / `action_score` in each trajectory file
  are the environment's genuine values — the acceptance decision is **not**
  written back into them.

## 8. Known limitations and upstream defects

### 8.1 The SFT loss is not masked to assistant tokens — BLOCKED, needs the file's owner

`sft_trainer.py` constructs `SFTConfig(...)` without `assistant_only_loss`, so
TRL computes the loss over the whole rendered chat: the model is trained to
predict the **tool observations** (user-role turns carrying retrieved evidence)
as well as its own actions. The RL arms mask non-assistant tokens.

This weakens the baseline and it should be fixed before the number is reported.
The fix is one keyword argument at `bioagents/training/sft_trainer.py:303`:

```python
sft_config = SFTConfig(
    output_dir=config.output_dir,
    assistant_only_loss=True,      # <-- add
    ...
)
```

**It was not applied here.** `sft_trainer.py` is outside this arm's ownership and
is shared with other arms; changing it would change their behaviour too. Raise it
with that file's owner. Until then, the rebuttal must disclose that the STaR arm
trains on unmasked trajectories.

### 8.2 `_compute_qa_accuracy` raises on tasks whose `options` is `null`

`agent_runner.py::_compute_qa_accuracy` does `task.get("options", {}).get(...)`.
The key is *present with value `null`* on 142/3390 train and 20/850 test tasks
(all `multimodal_vqa` with a ≤2-character gold answer such as `"no"`, `"T2"`), so
`.get` is called on `None` and raises `AttributeError`.

Scope, precisely: the function returns early on a match, so the crash fires
**only on incorrect rollouts**. `run_task` catches it, so the trajectory survives
but `compute_composite_reward` is never reached and the rollout has no
`reward_details` at all. Therefore:

* accuracy-based acceptance is **unaffected** — those rollouts are wrong and
  would have been rejected anyway;
* the composite and per-dimension **means are biased**, because those samples are
  missing from them;
* `verl_acc` / `verl_score` are **immune**, being computed in `star_generate.py`
  from the transcript.

`star_generate.py` counts these as `n_unscored_by_env_grader`, keeps them in the
acceptance denominator (dropping them would inflate the reported rate), and
prints them. `agent_runner.py` is owned elsewhere and was not patched; the fix is
`(task.get("options") or {}).get(...)`.

### 8.3 `trl` is not installed in the run venv

`sft_trainer.py` imports `trl` inside `train()`. It is absent from
`hcgym_rebuttal/.venv` (torch 2.9.1, transformers 5.3.0, peft 0.19.1, datasets
5.0.0, accelerate 1.14.0 are all present). `train_star.slurm` fails preflight
with the remedy rather than discovering it after hours of generation:

```
${VENV}/bin/pip install 'trl>=0.8'
```

It was **not installed by this arm**: the venv is shared with jobs that are
running now, and a `trl` install can drag `transformers` with it. Install it
deliberately, and re-run `tests/test_star_baseline.py` afterwards.
`ALLOW_NO_TRL=1` runs the generation half alone.

### 8.4 `trajectory_to_sft` drops the task ticket

`sft_generator.trajectory_to_sft` rebuilds messages from turns alone, and turns
carry no user question — so a `trajectory_dir`-sourced example is a system prompt
followed by tool calls **with no task in context**. It also truncates tool
responses to 2000 characters, on top of `_save_task_result`'s 500.

`star_generate.py` therefore writes **both** shapes and `star_iterate.py` defaults
to the faithful one:

* `trajectory_dir/` — per-task JSON in exactly the shape
  `trajectory_to_sft` consumes (`final_reward`, `action_score`, `turns`,
  `task_id`), so the pre-existing `trajectory_dir` + `min_reward` path works
  unmodified. `--sft-source trajectory_dir` uses it.
* `star_sft.jsonl` — the `sft_path` shape (also pre-existing, and *higher
  priority* inside `build_sft_dataset`), carrying the **exact message list the
  policy was shown**, captured by wrapping `runner.generate` rather than by
  re-deriving the prompt. System prompt, task ticket, every tool observation
  untruncated. **Default.**

`test_sft_path_shape_keeps_the_task_ticket_and_trajectory_dir_does_not` asserts
both halves of this, and will fail loudly if `trajectory_to_sft` is ever fixed —
at which point the default should be revisited.

### 8.5 Other

* `max_length: 8192` for SFT (repo default is 4096). A 5-turn episode with real
  tool observations exceeds 4096 tokens routinely; a measured 2-tool-call episode is 2,329
  tokens under the Qwen3.5-9B chat template. Sequences beyond 8192 are still truncated by TRL, silently.
* `max_samples: 200000` so `build_sft_dataset`'s default 5000-sample random
  subsample never fires unnoticed.
* Generation is single-request-per-episode: `k` samples are `k` separate
  `run_task` calls rather than one `n=k` server call. Throughput comes from
  `--workers` concurrent episodes against a `--dp-size 8` server.

## 10. Run

```bash
# preemption-resilient (state.json makes a requeue re-run at most one iteration)
SCRIPT=$RUN_ROOT/runs/train_star.slurm \
  ./runs/autoretry.sh q9b_star $RUN_ROOT/models/Qwen3.5-9B star

# or directly
sbatch --export=ALL,BACKBONE=$RUN_ROOT/models/Qwen3.5-9B,EXP=q9b_star \
       runs/train_star.slurm
```

Useful overrides: `ACCEPT_ON=composite_reward` (the format-adaptation variant —
prefer `--refilter-from`, which needs no rollouts), `POOL=…_textonly`,
`INIT_FROM=previous`, `DATASET_SCOPE=accumulated`, `MAX_ACCEPTED_PER_TASK=0`,
`ITERATIONS`, `SAMPLES_PER_TASK` (both change the budget claim in §5),
`DRY_RUN=1`.

Outputs under `$RUN_ROOT/baselines/STaR/$EXP/`:

| path | contents |
|---|---|
| `star_curve.json` | the per-iteration curve: acceptance rate, coverage, dataset size, held-out scores |
| `iter_NN/gen/gen_stats.json` | acceptance rate, score distributions + histograms, per-source-domain breakdown, counterfactual acceptance under every signal, budget accounting |
| `iter_NN/gen/all_scores.jsonl` | one line per rollout, every signal — the file `--refilter-from` reads |

## 11. What the rebuttal may and may not claim

**May claim**

* "We implemented STaR (Zelikman et al., 2022) against the Healthcare AI GYM and
  compared it under a matched rollout budget of 30,510 rollouts, the same
  backbone, the same 3,390-task training split and the same 5-turn budget as the
  RL arms."
* "Acceptance was on correctness alone (the GYM's own answer grader), not on the
  composite reward, because the composite ranks a wrong-but-fluent rollout above
  a correct-but-terse one on 52.5% of training tasks."
* "We additionally report the composite-accepted variant" — **only if it was
  actually produced with `--refilter-from` or a rerun.**
* Whatever the per-iteration curve in `star_curve.json` actually shows.

**May NOT claim**

* That the authors' STaR code was run, or that this is "the official STaR
  implementation". It is a reimplementation. Say so in the same sentence as the
  number.
* That this is *full* STaR. It is STaR **without rationalization** (§6).
* That a STaR loss refutes the null hypothesis. Rationalization can only add
  data, so this arm lower-bounds STaR's dataset; a loss is weak evidence and a
  match is strong evidence. State the asymmetry.
* That STaR was hyperparameter-matched to the RL arms on the *training* side.
  Rollout budget is matched exactly; gradient steps, LR and SFT epochs are not
  (§5).
* Any statement about the multimodal slice without the caveat in §3.7 — those
  tasks reach the policy as a file path, not as an image, in this rollout channel.
* Anything about the number that omits §8.1: the SFT loss is not masked to
  assistant tokens, which handicaps this arm relative to the RL arms.
